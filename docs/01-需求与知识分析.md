# 语音转文字工具 · 阶段一：需求与知识分析

> 状态：分析稿（未开始编码）
> 目标：把 4 条需求翻译成「需要掌握哪些知识」，并说明每项知识的用处与选型倾向。

---

## 一、需求拆解（把口语需求翻译成技术命题）

| 编号 | 原始需求 | 技术命题 | 隐藏难点 |
|---|---|---|---|
| R1 | 按快捷键开始/停止录音 | 全局热键监听 + 录音会话生命周期管理 | 热键被占用、误触、上一段还没处理完又按一次 |
| R2 | 说话自动变文字 | 音频采集 → VAD 切分 → ASR 转写 → 文本后处理 | 中文准确率、术语、标点、口语噪声 |
| R3 | 文字自动贴到光标处 | 目标窗口焦点还原 + 文本注入（剪贴板粘贴 / 模拟键入） | 不能破坏用户剪贴板、不能抢焦点、部分应用粘贴失效 |
| R4 | 屏幕底部小窗显示状态 | 悬浮窗（无焦点、置顶、高 DPI、多屏） | 悬浮窗一旦抢焦点，R3 就贴不回原位置了 |

> 关键洞察：**R3 与 R4 是互相打架的**。悬浮窗必须做到「显示但不夺焦点」，这是整个项目在 Windows 上最容易被做砸的一点，也是它区别于普通语音输入法的技术核心。

## 二、本机硬件基线（已实测，直接决定选型）

| 项目 | 实测结果 | 对选型的影响 |
|---|---|---|
| CPU | Intel i5-1340P（12 核 16 线程，P+E 混合架构，轻薄本低压 U） | CPU 推理可行，但只够跑小模型；满载会掉频、风扇起转 |
| 内存 | 15.7 GB | 够用；本地跑 1~2GB 级模型无压力，但不适合同时驻留多个大模型 |
| GPU | Intel Iris Xe 核显，**无 NVIDIA，无 CUDA** | 排除所有依赖 CUDA 的加速路径（faster-whisper GPU / whisper large） |
| 系统 | Windows 11 家庭版 build 26200 | 前面提到的所有 Win32 能力全部可用 |

**结论：本地识别只能走「小模型 + int8 量化 + CPU 多线程」路线。** 这是本清单里最重要的一条客观约束，它砍掉了一半的候选方案。

## 三、知识清单

按「缺了会怎样」组织，每条都标注：**用处 → 选型倾向 → 缺失后果**。

### 域 A｜Windows 系统交互（对应 R1 / R3 / R4）

**A1. 全局热键注册：`RegisterHotKey` vs 低级键盘钩子 `WH_KEYBOARD_LL`**
- 用处：让快捷键在任意程序前台时都生效。这是 R1 的唯一实现路径。
- 倾向：优先 `RegisterHotKey`（系统级、无驱动、不触发杀软）；它注册失败时（组合被微信/输入法/显卡驱动占用）必须能检测到并提示换键。低级钩子作为降级方案。
- 缺失后果：快捷键时灵时不灵，且用户不知道为什么。

**A2. 键盘模拟输入 `SendInput`**
- 用处：R3 的落地手段之一（模拟 Ctrl+V，或逐字符 Unicode 键入）。
- 必须知道的两条硬限制：
  1. UIPI 机制——普通权限进程**无法**向「以管理员身份运行」的窗口注入按键；
  2. 中文输入法激活状态下，部分应用（Electron 类、终端、部分游戏）逐字符注入会丢字。
- 缺失后果：在 VSCode 里能用、在某个编辑器里就是粘不进去，且查不出原因。

**A3. 剪贴板读写与**无损保全**（CF_UNICODETEXT / CF_HDROP / CF_BITMAP / HTML Format）**
- 用处：「写剪贴板 + 模拟 Ctrl+V」是所有方案里兼容性最好的注入方式。
- 关键认知：**必须先完整备份剪贴板所有格式，粘贴后原样恢复。** 用户此刻剪贴板里可能是一张图、一批文件、一段带格式的富文本——只备份纯文本再恢复，等于把用户的东西弄丢了。
- 缺失后果：这是最招人烦的副作用，会直接让工具被弃用。

**A4. 前台窗口与焦点管理（`GetForegroundWindow` / `SetForegroundWindow` / 输入法状态）**
- 用处：按下快捷键的瞬间记录「目标窗口句柄」，注入前把焦点还回去。
- 为什么必须有：用户点击悬浮窗、或悬浮窗动画导致焦点漂移，都会让文字贴到错误的地方。
- 缺失后果：文字贴进悬浮窗自己、贴到浏览器地址栏、或者干脆没反应。

**A5. 无焦点悬浮窗（`WS_EX_NOACTIVATE` + `WS_EX_TOOLWINDOW` + 置顶 + 高 DPI + 多显示器定位）**
- 用处：R4 的实现基础。
- 关键点：
  - `WS_EX_NOACTIVATE`：点击窗口不夺焦点（否则 R3 必废）；
  - DPI 感知：125% / 150% 缩放下不声明 DPI 感知，窗口位置会算错几十像素；
  - 多屏 / 任务栏位置（底部、左侧、自动隐藏）都会影响「屏幕底部」的坐标计算；
  - 不进 Alt+Tab 列表（`WS_EX_TOOLWINDOW`）。
- 缺失后果：窗口跑到屏幕外、被任务栏挡住、或者一点就把光标位置搞丢。

### 域 B｜音频采集（R2 的前半段）

**B1. Windows 音频采集（WASAPI / `sounddevice` / `pyaudio`，16kHz / 单声道 / 16bit PCM）**
- 用处：拿到识别引擎要的原始音频。
- 必须知道：主流 ASR 引擎统一吃 **16kHz 单声道 16bit**，采集端就要直接按这个格式要数据，避免后期重采样引入噪声。
- 缺失后果：识别率莫名偏低（采样率不匹配）、或设备热插拔（插拔耳机）后录音变哑。

**B2. VAD 语音活动检测（Silero-VAD / WebRTC VAD）**
- 用处：判断「这句话说完了没有」，用于静音自动停止、切分长语音。
- 为什么必需：**不做 VAD 直接整段送进识别，静音段会让模型「编造」文本**（Whisper 的经典幻觉问题）。写文章时一次说 30 秒，中间必有停顿。
- 缺失后果：凭空多出几句你没说过的话。

**B3. 环形缓冲（Ring Buffer）与「按键前 0.5 秒」预录**
- 用处：解决「按快捷键时第一个字已经被吃掉」的问题。
- 为什么值得做：采集流常开、只保留最后 0.5 秒。这是专业语音输入工具和业余作品的分水岭，成本极低。
- 缺失后果：每次都要重说第一句，体验立刻掉档。

### 域 C｜语音识别引擎（R2 的核心，本项目的技术重心）

**C1. 候选引擎全景与本质权衡**

| 路线 | 代表 | 中文准确率 | CPU 延迟（本机预估） | 隐私 | 成本 | 离线 |
|---|---|---|---|---|---|---|
| 本地·非自回归 | FunASR **SenseVoice-Small** | 高（中文专优，自带标点） | 极低 | 全本地 | 免费 | 是 |
| 本地·自回归 | **faster-whisper** small/medium int8 | 中（small 偏弱，medium 可用） | 中 | 全本地 | 免费 | 是 |
| 本地·轻量 | sherpa-onnx（Paraformer / Zipformer） | 中高 | 极低 | 全本地 | 免费 | 是 |
| 云端 | 阿里云 / 腾讯云 / 火山 / 讯飞 / OpenAI | 最高（大模型 + 热词） | 300ms~1.5s（含网络） | 音频出本机 | 按分钟计费 | 否 |

- 用处：这是决定「项目好不好用」的唯一分水岭，必须先把这条想清楚再写一行代码。
- 倾向（基于本机无 GPU）：
  - **主力：SenseVoice-Small（本地）**——中文准、CPU 快、自带标点，最贴 R2 诉求；
  - **备选/高精度档：云端流式接口**——涉密内容不能出本机时切回本地；
  - **Whisper 作为第三档**：多语种混说（中英夹单词）时它的鲁棒性更好。
- 缺失后果：选了 Whisper large → 本机一句 10 秒的话要等 20 秒，项目直接死掉。

**C2. 整段识别 vs 流式识别（以及「伪流式」）**
- 用处：决定交互形态。
- 三种形态：
  1. **整段**（松开快捷键后一次性出结果）：最简单、准确率最高（模型有完整上下文）；
  2. **分句伪流式**（VAD 切句，逐句识别逐句贴）：复杂度中等，首字延迟低；
  3. **真流式**（边说边出字并不断修订前文）：体验最好，复杂度高一个量级，且修订会导致光标处的文字反复跳变。
- 倾向：V1 做整段；V2 做分句伪流式；真流式留到 V3（在「贴到光标」场景下收益远小于代价）。
- 缺失后果：一上来就做真流式，会把项目拖死在一个体验并不重要的细节上。

**C3. 推理加速（int8 / fp16 量化、线程数、ONNX Runtime vs CTranslate2）**
- 用处：把「说完到出字」从 8 秒压到 1 秒。
- 必须知道：i5-1340P 是 P+E 混合架构，线程数开满 16 反而会因 E 核拖慢而变慢，通常 6~8 线程最优；且要限制功耗模式，避免长时间满载掉频。
- 缺失后果：笔记本风扇狂转、掉电飞快，工具不敢用。

**C4. 模型体积与加载策略（懒加载 / 常驻 / 首启下载 / 打包体积）**
- 用处：决定安装包能不能发出去。
- 必须知道：模型内置会让安装包到 300MB~1GB+；首启下载则要处理断网、校验、进度提示。
- 倾向：常驻内存（避免每次首字延迟多 1~3 秒），模型随包分发或首启下载（待定，见决策点）。

### 域 D｜文本后处理（决定「能不能真的用来写文章」）

**D1. 标点恢复与断句**
- 用处：ASR 原始输出常无标点或标点错乱，写文章必须有。
- 倾向：优先选自带标点的引擎（SenseVoice / Whisper 均自带），不要自己训模型；不足时用轻量规则补。

**D2. 口语清洗（嗯、啊、那个、就是说、重复词、自我修正）**
- 用处：**这是「语音输入法」和「能写文章的输入法」的分界线。** 口语直出成文字，几乎不能直接用。
- 手段两档：① 规则表（"嗯/呃/那个"删除、叠词去重）；② 轻量 LLM 润色（本地小模型或云端，可开关）。
- 倾向：V1 只做规则清洗（可预期、零延迟、不乱改内容）；LLM 润色做成可选开关，明确告知会改动原文。
- 缺失后果：转出来是一段需要手动重写一遍的口语，等于白做。

**D3. 文本规范化 ITN（数字、日期、金额、英文大小写）**
- 用处：「二零二六年十月十七号」→「2026年10月17日」；「百分之三十」→「30%」。
- 倾向：优先用引擎自带的 ITN 开关，不自研。

**D4. 热词表 / 上下文偏置（Contextual Biasing）**
- 用处：老板写文章必有专业术语、人名、产品名，通用模型会转错。Whisper 用 `prompt` 参数注入上下文，FunASR 用热词表。
- 为什么重要：这是「准确率从 90% 到 97%」性价比最高的一招，且完全不需要重训模型。
- 缺失后果：每篇文章都要手工改十几个专有名词。

**D5. 繁简与异体字统一（低优先级）**
- 用处：仅当涉及港台用语或需要统一字形。V1 跳过。

### 域 E｜应用架构（把上面串起来，工程纪律所在）

**E1. 显式状态机（`idle → recording → finalizing → transcribing → injecting → done / error`）**
- 用处：快捷键是「切换」语义。双击、误触、上一段还没识别完又按一次——**没有状态机必然出现一堆竞态 bug**（重入、重复粘贴、两段文字交错）。
- 倾向：状态转移必须单一入口、拒绝非法转移、并在悬浮窗上体现当前状态。
- 缺失后果：偶发的「一次按键贴出两段话」「文字贴到一半卡住」，且无法复现。

**E2. 并发模型（采集线程 / 推理进程 / UI 主线程 隔离）**
- 用处：推理是 CPU 密集，放主线程会冻结悬浮窗。
- 倾向：**推理放独立子进程**——可崩溃隔离、可强制超时终止（子进程卡死不影响主程序收录音）。
- 缺失后果：一句识别卡住，整个工具装死，只能杀进程。

**E3. 配置与持久化（热键、设备、引擎、语言、清洗强度、注入方式；JSON 配置 + 托盘菜单）**
- 用处：这些参数一定会在使用中反复调，硬编码等于每次改代码。

**E4. 日志与可观测（本地滚动日志 + 可选音频留存）**
- 用处：这类工具最典型的故障是「偶尔贴不进去」，没日志几乎无法定位。
- 倾向：默认记录状态转移与注入目标窗口信息；音频默认不落盘（隐私），排障时可临时开启。

**E5. 打包分发与单实例（PyInstaller / Nuitka、开机自启、单实例锁）**
- 用处：**单实例锁是必须的**——双开会抢热键、出现两个悬浮窗、贴两遍文字。

### 域 F｜安全与合规（写文章场景权重很低，但绕不开）

**F1. 密钥管理**：云端 API Key 存 Windows 凭据管理器 / DPAPI，绝不硬编码进源码或配置明文。
**F2. 隐私边界**：写文章内容可能涉密。**必须有「纯本地模式」并作为默认**，音频与文本是否上传要显式可见。
**F3. 杀软与权限摩擦**：低级键盘钩子和模拟输入是安全软件的高敏感行为（误报风险）；向管理员窗口注入需要提权。要提前决定「是否要求管理员权限运行」，并写进限制说明。

### 域 G｜本体 / 领域建模（你提到的四方面之一，这里先给草案）

把系统抽象成 6 个核心实体，模块边界就自动出来了：

| 实体 | 含义 | 关键属性 |
|---|---|---|
| `Hotkey` | 热键绑定 | 组合键、注册状态、冲突信息 |
| `Session` | 一次录音会话 | id、开始/结束时间、状态、目标窗口句柄 |
| `Utterance` | 一句话（VAD 切出的片段） | 音频缓冲、起止时间、是否静音 |
| `Transcript` | 转写结果（三级形态） | raw / punctuated / cleaned、引擎、置信度、耗时 |
| `Injection` | 注入动作 | 目标窗口、方法（paste/type）、成功与否、失败原因 |
| `Engine` | 识别引擎配置 | 类型（本地/云）、模型、语言、热词表 |

数据流：`Hotkey → Session → Utterance[] → Engine → Transcript → 后处理 → Injection → 目标光标`

这个模型的价值：**每一个箭头都是一个可独立测试的接口**，也是 V1 的模块划分依据。

## 四、路线对比（三选一，待你拍板）

| | 纯本地 | 纯云端 | 混合（推荐） |
|---|---|---|---|
| 隐私 | 最好 | 最差 | 可控（默认本地） |
| 中文准确率 | 高（SenseVoice） | 最高 | 高 |
| 首字延迟 | 0.5~2s | 0.3~1.5s（看网络） | 1s 左右 |
| 成本 | 0 | 按分钟计费 | 低 |
| 断网可用 | 是 | 否 | 是 |
| 开发工作量 | 中 | 低 | 中高 |

**推荐混合**，但**默认走本地**（写文章内容私密 + 本机 CPU 足够跑小模型）。云端只在老板主动切「高精度档」时启用。

## 五、需要你拍板的关键决策（影响架构，不宜由我猜）

1. **是否接受「纯本地 + 小模型」的准确率上限？** 本机无独显，这是硬约束。若能接受，V1 全本地、零成本、零隐私风险；若你要「几乎不用改字」的准确率，就必须引入云端引擎作为主力。
2. **要不要「边说边出字」（流式）？** 我的建议是不要——「贴到光标」场景下文字反复修订会很难受，整段出字更稳。请确认。
3. **注入方式偏好：剪贴板粘贴（兼容性最好，但会短暂占用剪贴板）vs 模拟键入（不占剪贴板，但个别应用会丢字）？** 我的建议是默认粘贴 + 无损兜底，键入作为可选。
4. **这个工具只给你自己用，还是要发给别人？** 只自用可以砍掉打包、自动更新、多用户配置；要分发则这部分工作量不小。

## 六、V1 建议验收标准（可度量，避免「感觉还行」）

| 指标 | 目标 |
|---|---|
| 说完到出字（10 秒语音） | ≤ 2 秒 |
| 中文常用句准确率（自测 50 句） | ≥ 92%（不改字即可用） |
| 热键响应 | 全场景（含全屏应用、远程桌面）100% 生效 |
| 注入成功率 | 在 Notepad / Word / 浏览器 / VSCode / 微信 五个场景 100% |
| 剪贴板副作用 | 粘贴后原剪贴板内容（含图片/文件）100% 还原 |
| 悬浮窗副作用 | 不夺焦点、不进 Alt+Tab、125%/150% 缩放下位置正确 |
| 连续使用稳定性 | 连续 100 次录音无卡死、无重入 |
