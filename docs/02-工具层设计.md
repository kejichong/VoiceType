## 四、五个关键实现决策

**1. 引擎 start 不阻塞 + 音频先入队**  
阿里云要「连 WebSocket → 等 TranscriptionStarted → 才能送音频」，全流程 0.3~1 秒。  
如果同步等待，用户按下快捷键后要愣一下才能说话。做法：start() 只起线程立即返回，  
音频打进队列，连接完成后按序补发 —— 说话不等人。

**2. 0.5 秒预录环形缓冲**  
麦克风流常开，deque 始终保留最近 5 个 100ms 块。按下快捷键的瞬间把这些块先吐给引擎，  
第一个字不会被吃掉。这是「专业工具」和「玩具」的分界。

**3. 剪贴板全格式快照，不是只备份文本**  
`ClipboardSnapshot` 枚举所有 HGLOBAL 类格式（UNICODETEXT / DIB / HDROP / HTML Format / RTF…）  
逐份复制内存，注入后原样写回。GDI 句柄类（CF_BITMAP）无法按内存备份，跳过；  
但存图的程序通常同时写 CF_DIB，所以图片仍可还原。  
另有安全网：还原前检查剪贴板是否还是我们写的那段文字，若用户已手动复制新内容则不覆盖。

**4. 状态机拒绝非法迁移**  
快捷键是「切换」语义，双击/误触/上一段未完成又按都会发生。  
`StateMachine` 用白名单表控制迁移，TRANSCRIBING 状态下再按快捷键直接忽略，  
从根上消掉「一次按键贴出两段话」。

**5. 悬浮窗是「玻璃」，不是「窗口」**  
`Qt.WindowTransparentForInput | Qt.WindowDoesNotAcceptFocus | WA_ShowWithoutActivating`

- 鼠标穿透。它永远不会把光标从编辑器里抢走——这是需求 3 和需求 4 能共存的前提。  
  所有交互（设置/退出/手动开关）都放托盘，不在悬浮窗上放按钮。

## 五、识别链路

```
热键 → 记下目标窗口句柄 → 建引擎(非阻塞) → 开流
   → 每 100ms 一帧 PCM(3200B) → WebSocket 送阿里云
   → 中间结果(SentenceEnd 累加) → 松开热键
   → StopTranscription → 等 TranscriptionCompleted
   → 后处理(去口水词/标点归一/补句号)
   → 备份剪贴板 → 写剪贴板 → 拉回目标窗口 → Ctrl+V → 延时 → 还原剪贴板
```

音频规格：16kHz / 单声道 / 16bit PCM / 100ms 一包（阿里云建议值）。

## 七之二、启动可见性与单实例唤醒

托盘程序最容易踩的坑是"**点了没反应**"——程序明明在跑，用户却认为没打开。

三个约束叠在一起会产生这个问题：托盘图标在 Win11 默认折叠进 `^`；程序本身没有主窗口；  
单实例锁命中时如果只是 `return 0`，第二次双击就是彻底的静默失败。

处理办法：

| 机制          | 实现                                                                                 | 解决什么                      |
| ----------- | ---------------------------------------------------------------------------------- | ------------------------- |
| 启动可见反馈      | `overlay.notice("已就绪 · <热键>", 3200)` + 托盘气泡                                        | 让用户确认"它起来了"               |
| 重复启动唤醒      | 命名事件 `Local\VoiceType_Wake_v1`：新实例 `SetEvent` 后退出，已有实例 50ms 轮询到就 `open_settings()` | 第二次双击不再石沉大海               |
| 托盘单击 = 打开设置 | `QSystemTrayIcon.Trigger/DoubleClick → on_settings`                                | 录音走热键，避免误触                |
| 设置窗口防重入     | `_settings_dlg` 引用检查 + `raise_()`                                                  | exec 的嵌套事件循环里 QTimer 仍会触发 |
| 热键失败不报"就绪"  | `_hotkey_ok` 标志                                                                    | 否则"已就绪"会盖掉真正的错误提示         |

开机自启由 `app/startup.py` 负责，写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`：  
打包后指向 exe 本身，开发态指向 `pythonw.exe run.py`（不弹黑框）。写失败弹警告但不阻断保存。

## 七之三、悬浮窗必须「按下即出现」

这是用户反馈最多的一处，也是最能说明「能用」和「好用」差别的地方。原话：

> 这个声音是第一时间就出来了，但是这个识别框就是人用眼睛可以看到的，它没有出来。

一个状态指示器，如果它出现得比声音还晚、甚至要等你开口说话才出现，那它就不叫状态指示器，叫噪音——用户会以为没启动成功，再按一次，于是第一次录音被掐断。

背后是三个独立原因叠加，必须同时解决：

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| 按下后主线程还在排队 | 热键回调跑在 `RegisterHotKey` 的消息线程，原先扔进队列，主线程 **50ms 轮询**一次才取到 | 改成 Qt 信号跨线程投递，`emit()` 立刻唤醒事件循环 |
| 绘制排不上队 | `show()` / `update()` 是**异步排队**，紧接着的 `recorder.open()` 在主线程同步阻塞几百毫秒，绘制轮不到执行 | `repaint()` 同步绘制，绕开事件队列 |
| 窗口要重新映射 | 空闲时 `hide()` 会**销毁原生窗口**，下次 `show()` 得重新创建并合成 layered window，这几百毫秒屏幕上是空的 | **窗口常驻**，空闲态画成全透明而不隐藏 |
| 帧交出去了但没上屏 | `repaint()` 只是把帧交给系统，DWM 要等到下一个垂直同步才推到屏幕，而这段等待正好被后面的阻塞吃掉 | 画完先让出 40ms 事件循环（`QTimer.singleShot`），再开设备 |

还有两个容易忽略的顺序问题：

- `winsound.Beep()` 是**同步阻塞**的，响 45ms 就堵 45ms。它必须排在绘制**之后**，否则等于把「框出现」硬生生推后 45ms。
- 目标窗口句柄必须在**按下那一刻**取。开设备被推迟了 40ms，等推迟结束再取，用户可能已经切走了窗口。

透明态的画法有个坑：清屏必须用 `QPainter.CompositionMode_Source` 铺一层全透明像素。默认的 `SourceOver` 是叠加语义，透明像素叠不上去，上一帧的圆角框会留在 layered window 上变成一块残影。

**验证方式也换了**：以前统计 `paintEvent` 被调用了几次，那证明不了用户看得见——调用过了和推到屏幕上是两回事。现在 `tests/smoke_overlay_on_screen.py` 和 `tests/test_exe_overlay_press.py` 直接**抓屏做像素差分**：先截一张"没框"的底图，再数框所在区域有多少像素变了。实测：

```
源码进程：按下 -> 屏幕像素改变      59 ms
打包 exe：Ctrl+Alt+Space -> 可见    60 ms（改信号前是 166 ms）
空闲态 / 收起后 与底图差异           0 像素
```

写这个测试时自己踩了三个坑，都值得记下来，因为它们都会让测试**假失败**，而假失败会误导你去改本来正确的产品代码：

1. `SPI_GETWORKAREA` 返回**物理像素**，`QScreen.availableGeometry()` 返回**逻辑像素**。本机 150% 缩放（2160×1368 物理 / 1440×912 逻辑），混用会截到完全不相干的区域。
2. `QScreen.grabWindow` 传子区域时 `x/y` 与 `w/h` 的缩放语义含糊。改成**全屏抓 + 手动按 dpr 裁剪**，没有歧义。
3. 启动时悬浮窗会显示 3.2 秒的「已就绪」提示，**和识别框是同一块区域**。不等它收起就取底图，底图本身就是深色卡片，按键前后差分为 0 —— 会误判成"框没出现"。判定条件必须是"该区域亮度回到桌面本色"，不能靠 sleep 猜时间。

## 七之四、悬浮球：点一下就行的入口

需求上只是「按快捷键就能开始/停止录音」，但真用起来用户反馈三键组合按着费劲。
先查了一遍键盘：好按的两键组合基本全被占了。

| 组合 | 被谁占着 |
| --- | --- |
| `Ctrl + 空格` | 输入法中/英文切换 —— 抢了就没法打中文 |
| `Alt + 空格` | 系统窗口菜单（还原/最大化/最小化/关闭） |
| `Shift + 空格` | 输入法全角/半角切换 |
| `Win + 空格` | 系统语言切换 |
| `Alt + 字母` | 各软件菜单栏快捷键，全局抢了会把人家的菜单弄坏 |

空着的是 `Alt+;` `Alt+.` `Alt+'` `Alt+,` 这类标点组合（`tests/check_hotkey_slots.py`
可以逐个试注册，实测本机哪些还空着），但都不如直接点一个球来得省事。

### 唯一的技术难点：点了不能抢焦点

这是整个功能**成败所系**，不是细节。程序靠"按下那一刻的前台窗口"决定把文字贴到哪。
点球的一瞬间如果 Windows 把前台窗口切给了球，`get_foreground_window()` 拿到的就是球自己，
文字会贴进空气里 —— 用户看到的是"球变红了，但一个字都没进来"，比不能点还糟。

三层保障：

1. **窗口带 `WS_EX_NOACTIVATE`**（Qt 里写作 `Qt.WindowDoesNotAcceptFocus`）。
   带这个扩展样式的窗口被点击时不会成为前台窗口，焦点留在原来的编辑器里。
2. **主控持续跟踪"上一个不是我们自己的前台窗口"**（`_last_foreground`，50ms 轮询更新，
   把悬浮窗和悬浮球自己的句柄排除掉）。悬浮球发起的会话用它当注入目标，
   只有当它失效（窗口已关、跟踪还没跑到第一帧）时才退回即时取值。
3. **注入前 `injector.inject_text` 本来就会 `set_foreground_window(target)`**，
   即便前两道都失守，文字也不会贴错地方。

热键路径不改用跟踪值——按下那一刻的前台窗口就是最准的，50ms 的跟踪延迟反而是累赘。
所以 `toggle(from_button: bool)` 带一个来源标志，两条路径各用各的取值策略。

### 交互细节

- 画布 68px，可见的球 48px（半径 24），四周各留 10px 透明给阴影和光晕。
  平时 68% 不透明度（不挡视线），鼠标移上去变实心；录音时红色 + 呼吸光圈，
  图标从话筒变成"停止"方块。
- 拖动阈值 5px：位移超阈值算拖动（结束时把位置写进配置），没超算单击。
  否则手抖一下就变成"点了一下"，会误触发录音。
- 右键菜单：设置 / 隐藏这个球 / 退出。隐藏会写进配置。
- **托盘右键新增「显示悬浮球」勾选项**：球平时半透明，用户一时找不到它时，
  唯一的恢复入口若埋在设置窗口里等于没有。勾选状态由主控单向同步，
  `setChecked` 前必须 `blockSignals`，否则会回调主控、主控再同步回来，来回抖动。
- 换显示器或改分辨率后，上次保存的位置可能跑到屏幕外 —— 显示前会把坐标夹回工作区内。
  默认落点按"可见的球"贴边算，不能拿画布宽度去减，否则会离屏幕边缘多出 10px 空隙。

### 画法上踩的三个坑

都是肉眼一眼能看出、但断言测不出来的类型，所以补了 `tests/check_ball_visual.py`
把几何和亮度做成指标。

| 坑 | 表现 | 原因 |
| --- | --- | --- |
| 光晕画在画布外 | 录音时的呼吸光圈完全看不见 | 旧版画布只有球那么大（52px），光晕画在 `(-3,-3,s+6,s+6)` 上，直接被裁掉。**画布必须比球大一圈** |
| 图标歪 | 麦克风看着不对称 | 图标坐标全用 `int()` 取整，48px 上误差累积。改成浮点坐标 + `translate/scale` 到设计坐标系 |
| 球是一坨黑 | 完全没有体积感 | `QRadialGradient(cx, cy, 中心半径, fx, fy, 焦点半径)` **参数顺序写反了**——中心圆必须是大的、焦点圆小而偏左上，写反了渐变直接退化 |

第三个最隐蔽：球被画成纯黑，其余一切正常，只有真的去看才会发现。

**顺带一个测试上的坑**：`QWidget.grab()` 和 `render()` 都会先把 widget 背景铺成不透明的
Qt 默认灰 `(227,227,227)`，透明通道全丢 —— 于是"球外一圈有没有光晕"这种判断会恒成立，
测试等于没测。`render()` 传 `DrawChildren` 也没用，这是顶层窗口（`Qt.Tool`）的固有行为。
所以绘制主体抽成了 `_paint_to(painter, size)`，测试直接对一张透明 `QImage` 作画。
另外读像素必须用 `img.pixelColor(x, y)`：`QColor(img.pixel(x, y))` 的 alpha **恒为 255**，
所有依赖 alpha 的判断都会失真。

### 验证

`tests/smoke_floatbtn.py` 用**原生鼠标事件**（`mouse_event`）点，不用 `QTest.mouseClick`——
后者是进程内合成事件，根本不经过 Windows 的窗口激活路径，测不出抢焦点这个问题。

实测结果，最后一条是对照组，用来证明前面的 PASS 不是蒙的：

```
前台窗口：点击前 0x5119c -> 点击后 0x5119c      ← 悬浮球没抢走焦点
对照组（故意去掉 NoActivate）：0x160e16 -> 0x2060e  ← 立刻被搅动，测试有牙齿
```

`tests/e2e_floatbtn.py` 再跑一遍完整链路（假引擎）：点球 → 录音 → 再点球 → 识别 →
注入，最后断言**目标编辑器里出现了文字**。这才是这个功能成不成立的唯一标准。

## 七之五、分发：免安装与发给别人

### 是绿色版，但必须是整个文件夹

PyInstaller onedir 产物：`VoiceType.exe`（4.7 MB 启动器）+ `_internal`（123 MB 全部依赖）。
**只拷 exe 一定挂** —— 启动器要找同目录的 `_internal` 加载 Python 运行时和 Qt。

放桌面的正确姿势是建快捷方式，不是拖文件：拖动是"移动"，会把 exe 从 `_internal`
旁边挪走，程序当场废掉。建议先把整个文件夹固定到 `D:\Tools\VoiceType` 这类位置
（留在项目的 `dist` 里会被构建产物清理一起删掉），再右键 → 发送到 → 桌面快捷方式。

### 密钥不会跟着走 —— 双层保障

1. 配置目录是 `%APPDATA%\VoiceType\config.json`（可用 `VOICETYPE_HOME` 覆盖），
   **不在程序目录里**。实测在 `dist` 内 grep `access_key_secret` 零命中。
2. 密钥用 Windows DPAPI 按当前用户加密，配置里是 `enc:` 前缀的密文，
   **拷到别的机器上解不开**。

结论：程序目录可以放心发出去，没人能刷你的阿里云账单。

### 但对方拿到不能用 —— 首启向导

默认配置 `engine.type=aliyun` 且三个密钥为空串。实测新用户（`VOICETYPE_HOME` 指向空目录）
一按录音就抛 `EngineError: 阿里云密钥未配置…`，对方不知道去哪申请、去哪填。

所以加了引导（`SettingsDialog(guide=True)`）：

- 触发：启动后自检 `_engine_ready()` 为假 → 自动弹设置窗；之后每次按录音也会先检查，
  没配齐就直接弹引导窗，而不是甩一句报错
- 内容：把"去哪个网址、点哪里、拿哪个值"写死在窗内（可点击链接），
  三个必填框描橙色边框，光标自动落到第一个空框
- 假引擎不算未配置 —— 它本来就不联网，不该弹这个

## 八、已知限制

1. 向「以管理员身份运行」的窗口注入会被 UIPI 拦截（普通权限进程无解），需以管理员身份运行本程序。
2. 中文输入法激活时，少数 Electron 应用对 Ctrl+V 处理异常（已留 `type_text` 逐字注入备用）。
3. 阿里云 Token 有效期 24 小时，程序内缓存并自动刷新；长时间挂机后首次识别可能多花 200ms。
4. 无网络时识别直接失败（云端路线的固有代价），错误会明确提示而不是静默失败。
